Frontend Security Checklist

A practical frontend security checklist covering public HTML, CSS, JavaScript, browser storage, third-party scripts, CSP and source maps.

Frontend security is not only about a framework. It is the combined result of browser-delivered markup, JavaScript, third-party scripts, storage choices, headers, build artifacts and backend assumptions. Use this checklist during development and before publishing a new build.

Core frontend security checks

  • Never place private keys, admin SDK credentials, database passwords or privileged bearer tokens in browser-delivered code.
  • Use a response-level Content-Security-Policy and review script-src, connect-src, frame-ancestors and form-action.
  • Treat localStorage and sessionStorage as browser-readable data, not an authorization boundary.
  • Review innerHTML, document.write, eval, dynamic functions and user-controlled URL schemes.
  • Minimize third-party scripts and verify iframe sandbox, referrer policy and provider restrictions.
  • Review source maps and deployment artifacts before making them public.

Turn the checklist into a project review

Use the CodeShield analyzer to scan an authorized public URL or import a local ZIP. Findings link back to the source inventory; the workspace lets you search, edit or remove a local file before exporting a review copy.

Quick pre-launch list

  • No private keys, tokens or passwords anywhere in HTML, CSS or JavaScript.
  • Source maps are not publicly deployed unless you intend it (source map guide).
  • Third-party scripts are limited, pinned and reviewed.
  • Forms and inputs are validated again on the server.
  • Security headers such as CSP and Referrer-Policy are set (header guide).
  • Debug pages, test files and backups are not left in the public folder.
